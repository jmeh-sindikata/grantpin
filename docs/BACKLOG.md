# Backlog

Ideas and known gaps that are deliberately not in v0.1. Each line says why it was deferred. Items marked **gap** are shortcomings of the current code that the docs describe rather than hide; the others are features.

## Roadmap (agreed 2026-10-25)

In this order, one at a time:

1. **Manual macOS hardware test** (docs/MANUAL-TEST-MACOS.md). Report the outcome letter; it decides whether Secure Enclave needs a signed bundle.
2. **Real Claude Code run** via the MCP shim, proving the README five-minute path.
3. **Daily use** for a week; collect friction.
4. **Native macOS menu-bar app (SwiftUI)** as v0.2, overriding the v0.1 "no GUI" non-goal. Talks to the daemon over the socket (docs/PROTOCOL.md): secrets add/edit/delete, grants with revoke, audit viewer, status and install-at-login. Ships as a signed `.app` bundle containing the daemon, which also answers the Secure Enclave entitlement question. The manual test came out as outcome D (ad-hoc signing is not accepted as a keychain access group, `-34018`), so the signed bundle is now also required to get the Secure Enclave at all; this makes it a security item, not only a UI item. The v0.2 bundle will be signed with a Developer ID Application certificate and a provisioning profile carrying `keychain-access-groups`, which restores the Secure Enclave and the hardware tier. The approval dialog later moves from `osascript` into the app. Rationale: the agent never needs the CLI, but humans who will not open a terminal must still be able to put secrets in.
   4a. (optional, earlier) **Minimal `.app` wrapper around the existing CLI daemon**, signed, launchd pointed at the bundled binary. This gives the Secure Enclave before the UI exists. **DONE 2026-10-25.** The bundle was signed with an Apple Development certificate and a macOS App Development provisioning profile, and the Secure Enclave is confirmed: `init` printed `keystore tier: hardware`. A Developer ID Application certificate is still needed for distribution (notarised, runs on other Macs). The fallback to Secure Enclave migration was done by re-init and re-set of each secret; a `grantpin migrate`/export command remains a backlog item (see "Migrate a vault between key stores").
5. **Security hardening** from the gaps below, informed by 1 to 3.
6. **Linux, then Windows backends**, then the socket-forwarding guide (HANDOFF §11 v0.2 to v0.4, now shifted one version later).
7. **Publishing**: GitHub, CI on macOS runners, Homebrew, auto-update. The signed, notarized DMG pipeline exists (`make release`, [RELEASE.md](RELEASE.md)), and a tag `vX.Y.Z` now gives a numeric `CFBundleShortVersionString`/`CFBundleVersion` and a `grantpin-X.Y.Z.dmg` name; still open: running it against the real Developer ID profile and notary credentials, `diskutil image` instead of the deprecated `hdiutil create`, and a release job in CI. Homebrew: the tap `jmeh-sindikata/grantpin` (repo `homebrew-grantpin`, a cask) exists, so `brew install --cask jmeh-sindikata/grantpin/grantpin` works; the remaining step is submitting the cask to the official homebrew-cask once the repo meets its notability bar.

## Security gaps

- **Detect replay of a genuine grant row (gap).** Grant rows are MAC'd (HMAC-SHA256 under `vault.DeriveKey("grant-mac")`), so forged or edited rows never match, but a row (or the whole file) saved earlier can be written back to revive a revoked grant or reset `uses_remaining` until the row's own expiry (THREAT-MODEL 4.5). Fix: a monotonic counter or generation number bound into the MAC and anchored somewhere the file-write attacker can't roll back (the Keychain, the audit chain head). Matters more now that standing grants (`grants add`) last up to 90 days, so a replayed row can revive a revoked grant for months rather than an hour. Deferred: bounded by the grant TTL, and it needs the same external anchor as the audit truncation item below.
- **Audit external anchor.** Periodically publish or sign the chain head (to a file outside the vault, a remote, the Keychain) so truncation of the newest rows is detectable. Deferred: needs a place to anchor that the vault-file attacker can't also write, which is a product decision.
- **Presence-gate `set`, `delete`, overwrite and `grants revoke` (gap).** Today a same-user process can destroy or replace secrets and drop grants (DoS and integrity, not disclosure). Gating them needs an approval flow with its own prompt text and an exemption for first-time `set` by the human. Deferred to keep v0.1's surface small; recorded in the threat model.
- **User-level policy the repo can't override.** Policy lookup uses the nearest `.grantpin.yml`, so an agent that can write files can shadow a stricter parent. A policy kept outside the repo (or intersected with it) would remove that. Deferred: it changes the policy model.
- **Bind the vault key to user presence or to a stronger code identity.** The Secure Enclave key has no user-presence flag by design (the daemon must unwrap it unattended), and an ad-hoc signature is a weak identity. Options: Developer ID plus a provisioning profile so the keychain access group is tied to a team ID; a presence-gated unwrap with a prompt at daemon start. Deferred: needs signing infrastructure and a decision about unattended start.
- **Hardened runtime for the signed binary (done for the bundle, open for `make sign`).** `make sign-bundle` and `make sign-release` sign both bundles with `--options runtime` and no exception entitlements, checked by `build/release/verify-signing.sh` (docs/RELEASE.md). Not yet exercised: the hardened-runtime build starting with the Secure Enclave and the Developer ID profile (needs the real profile). The ad-hoc `make sign` for `bin/grantpin` still omits `--options runtime`; it is a dev path and stays so.
- **MinTier binding for `Get`/`List` metadata.** `min_tier` is bound into the GCM data and verified when a secret is decrypted for a release, but `list` and `Vault.Get` return the column unverified. Binding it (for example a metadata MAC) would make displayed tiers trustworthy. Deferred: displayed value only; releases already verify.
- **Authenticate secret metadata.** `expires_at`, `url`, `notes` and tags are not covered by the GCM tag, so a file-write attacker can extend an expiry. A metadata MAC like the one on grant rows would fix it.
- **Per-secret `--min-tier none`.** `set --min-tier none` currently means "vault default", and `TierNone` can never be stored on a real vault, on purpose. A deliberately unprotected secret (for example a non-sensitive token an agent may use after a plain dialog) would need an explicit opt-in. Deferred: the conservative choice was to disallow it.
- **Process sandboxing and network egress control for approved commands** (HANDOFF §2, "v2 candidate"). The approved-command-exfiltrates hole can't be closed by approval alone. Deferred: large, platform-specific.
- **Redact common encodings** (base64, hex, URL-encoded forms of each value) as extra defence in depth. Never complete; deferred because it adds false positives and would suggest a guarantee that doesn't exist.

## Behaviour and usability

- **Show the policy file path in the dialog.** The dialog states whether a policy exists and the grant scope, but not which `.grantpin.yml` applied (or that a nested one shadowed a parent). Deferred; the dialog text is near its length budget.
- **`service install` PATH is a snapshot.** It records the installing shell's `PATH` (or `--path`); later changes to your `PATH` need a re-run of `install`. Deferred: a live PATH would let the requester influence the child's environment.
- **Atomic import over the socket.** `vault.Import` is transactional, but `grantpin import` sends one `set` per key, so a daemon error midway can leave a partial import. Needs an `import` op. Deferred: the CLI pre-checks names and conflicts, which covers the usual failure.
- **Relay signals beyond INT/TERM.** `grantpin run` turns SIGINT/SIGTERM into a closed connection, which makes the daemon stop the command's process group (SIGTERM, then SIGKILL after 2 seconds). SIGHUP, SIGUSR1, SIGWINCH and others are not forwarded. Needs a signal frame in the protocol and an authorisation story. Deferred.
- **Auto-started daemon environment.** The MCP shim forwards a short allow-list of variables and drops `GRANTPIN_HOME`, and the daemon's output goes to `/dev/null`. Add a log file for it. (MCP log file for the auto-started daemon.)
- **Duration choice in the "Allow for N" dialog.** The duration is now configurable through the policy's `max_grant_ttl` (capped at 24h; default 1h), but the dialog still offers a single fixed value. Letting the human pick a duration per prompt needs UI. Deferred.
- **Dialog button for use-limited grants ("Allow N times").** Use-limited grants exist via `grantpin grants add --uses N`, but the release dialog has no button for them. Deferred: needs UI (the native app).
- **Migrate a vault between key stores.** The fallback to Secure Enclave move was done by hand (re-init and re-set each secret). A `grantpin migrate`/export command is still missing: a command that re-wraps the data key under the new keystore would avoid that (MANUAL-TEST-MACOS.md §2c (g)). A command to remove the Secure Enclave key is also missing: the key lives in the data-protection keychain, invisible to `security`, and only the signed bundle's binary can delete it. Deferred: the one-off manual migration is done.
- **Purge expired grants.** `grant.Store.Purge` exists but is never called; expired rows stay in the table (they are ignored). Trivial; deferred.
- **NSAlert-based chooser instead of `osascript`.** A native alert from the daemon (or a helper app) would avoid `osascript` and give control over the layout and the default button. Deferred: needs an app bundle for a proper UI process.
- **Interactive input for the child.** The child's stdin is `/dev/null`. Deferred.
- **Audit export over the socket is capped at 1 MiB**; larger logs need `audit list --limit` or paging. Deferred.
- **Windows-specific code paths** (`policy` ownership check, process groups, named-pipe transport) are stubs. Part of the Windows backend.
- **Automatic service restore, known small gaps (review of v0.2.4, 2026-10-27).** The app looks for `service.wanted` and `vault.db` only in `~/Library/Application Support/grantpin` (`AppPaths.vaultFolder()`), while the CLI honours `GRANTPIN_HOME` and `XDG_DATA_HOME`, so a service installed from a shell with either set is never restored by the app although `service status` says `wanted: yes`. The app also requires both files to be owned by the current user, which Go's `service.Wanted` does not check. During the 10 s pending window after a restore, a daemon the person starts by hand is recorded as the automatic restore. `noteAsked()` runs when the gate says ask even if `presentServiceAsk` then declines (popover opened or state changed during its poll), which gives up the restore for that outage without a window. If the monitor's loop poll is already in flight, the pending-deadline `refreshNow()` returns at once and the decision may use a state that poll is about to replace. "Restored automatically on" in Settings lasts only for the current launch (`restoredAt` is in memory). Deferred: all narrow or cosmetic; the one that matters most is the data-directory mismatch, which is a CLI-and-app decision about whether the app should honour the environment variables at all.
- **Service restore code structure (review of v0.2.4).** The restore's `popoverOpen` closure still reads the `AppModel.current` global with a `?? false` fallback because `self` is unusable in `init`; the popover's own `onChange` and the `uninstallOpen` flag on `ServiceActivity` are a second surface registry beside `visibleSurfaces`; the "Restored automatically on" line in Settings is assembled in the view from `restoredAtPrefix` rather than produced by the Kit like `noticeText`, and renders outside the Form's `Hint` style. Deferred: no behaviour change, but worth one tidy-up commit.

## Platforms

- **Linux (v0.2).** Secret Service (libsecret) key store with an optional TPM2 and an Argon2id passphrase file as the last resort; a native dialog approver (`TierDialog`); systemd `--user` unit. The seams (`keystore.KeyStore`, `approve.Approver`, `service.Manager`) already exist and the peer-credential check has a `SO_PEERCRED` implementation.
- **Windows (v0.3).** DPAPI (optionally CNG/TPM) key store, Windows Hello `UserConsentVerifier` approver, `go-winio` named pipe with a current-user ACL, a startup task.
- **Socket forwarding guide (v0.4).** How to expose the daemon to devcontainers, WSL and SSH sessions without weakening the peer check.
